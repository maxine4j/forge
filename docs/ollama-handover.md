# Ollama inference provider implementation handover

## Objective and current state

Add Ollama as a second inference provider in Forge. Keep the existing OpenAI / ChatGPT account sign-in available alongside the saved Ollama configuration. Give the owner one global selector that determines which provider newly created agents use. Reuse the existing Codex app-server harness for both providers.

Implementation has stopped at repository inspection and protocol probes. No application code was changed. The owner is setting up Ollama locally. Leave that setup alone and avoid connecting to it, starting it, or pulling models until the owner explicitly asks for live verification. Use credential-free Codex probes, controlled app-server peers, and browser fixtures during implementation.

Initial scope covers standalone chats, ticket planners, and ticket implementers. Automatic fallback, per-ticket provider selection, multiple Ollama models, discovery, endpoint credentials, and live connection testing in Config are out of scope.

## Verified findings

- Forge runs the repository-pinned `@openai/codex` **0.164.0** over a single private stdio JSON-RPC connection. Use `./node_modules/.bin/codex` after `nvm use` for any protocol verification. The desktop `codex` on `PATH` was a different build.
- A credential-free probe started an OpenAI thread and a custom Ollama thread on the same app-server. The Ollama `thread/start` request passed `modelProvider: "forge_ollama"`, `model: "gpt-oss:20b"`, and `config.model_providers.forge_ollama` with `name: "Ollama"`, `base_url`, `wire_api: "responses"`, and `requires_openai_auth: false`. The returned thread and response identified `forge_ollama` and the response selected the requested model. The probe used `config.web_search: "disabled"`. The model tag was an example, so keep the actual tag owner-configurable.
- With OpenAI as the app-server startup provider, `account/read` remained available and reported `requiresOpenaiAuth: true` after the Ollama thread started. A separate probe with Ollama as the startup provider reported `requiresOpenaiAuth: false`, but `model/list` still returned OpenAI models. Keep OpenAI at app-server startup and apply Ollama settings to individual threads.
- These probes exercised initialization, account reads, catalog reads, and thread creation only. They did not exercise inference, resume after process restart, credentials on inference requests, tool calls, Plan mode, or automatic approvals.

See the [Codex app-server protocol](https://learn.chatgpt.com/docs/app-server), [Codex provider configuration](https://learn.chatgpt.com/docs/config-file/config-advanced), and [Ollama Responses compatibility](https://docs.ollama.com/api/openai-compatibility). Ollama must support `POST /v1/responses`, including streaming and function calls for Forge's workflows.

Treat the value as the Responses API base URL, for example `http://ollama.internal:11434/v1`, and document the expected `/v1` suffix. Preserve support for container-reachable internal addresses. Save the settings without performing a network request.
3. Label the existing OpenAI model and thinking defaults so their scope is clear. Keep existing ticket instructions, cost settings, refresh, validation, and save behavior. Account card buttons need `type="button"` if placed inside the settings form.
4. Reuse owner and origin checks on `GET /api/settings` and `PUT /api/settings`. Retain the OpenAI catalog for the OpenAI defaults form. Refresh the new-agent options after a provider change using the existing `AgentOptionsRevision` context.

## Thread routing and persistence

1. Inject the current inference settings into `AgentService` from `src/start.ts`. In `AgentService.createThread`, snapshot the provider for every standalone and managed agent. Save the endpoint and model for Ollama in the internal `AgentThreadRecord` and its SQLite JSON schema. Treat missing provider data on existing records as OpenAI. Exclude the endpoint and internal provider configuration from public agent responses. Keep the endpoint and model stable for that thread if the owner edits Config later.
2. Standalone Codex thread creation is lazy. A Forge chat created before a switch retains its original provider when it receives its first message. Ticket planning and implementation create separate agent records, so each takes the current provider when its record is created. Clarifications, follow-ups, and recovery reuse the provider on their existing thread.
3. Extend `ICodexAgentClient` and `CodexAgentClient` in `src/codex/codex-agent-client.ts` to use the saved provider at `start`, `resume`, and `reconcile`. Pass it through every corresponding call in `src/agents/agent-service.ts`, including startup recovery and Stop all agents. The OpenAI path can retain its current RPC payload. For Ollama, send the model, `modelProvider`, and a thread-scoped provider definition. Extend the strict request schemas in `src/accounts/codex-connection.ts`. Verify `thread/resume` fields against the pinned CLI's generated protocol and test resume after a fresh process. Where the runtime returns provider identity, validate it on the Ollama path to catch accidental routing to OpenAI.
4. Keep current execution reservations, per-thread serialization, worktree checks, approval callbacks, history pagination, and no-replay recovery. A settings save must not restart app-server or interrupt an active turn. Endpoint failures should surface through existing agent error and recovery paths. Preserve the existing rules for ambiguous dispatch and never retry a turn against a different provider.

## Model selection, approvals, and usage

- Continue using app-server `model/list` for OpenAI. Supply a one-entry catalog from the saved configuration for Ollama, with the configured tag as the default. Keep worktree skill discovery through app-server. Use the record's catalog for chat options and turn dispatch and the current global provider for options for a new agent. Do not send OpenAI reasoning defaults to Ollama. Expose no Ollama effort choices until support is verified.
- The ticket workflow has existing model and thinking overrides. Keep those settings and reject incompatible explicit values at dispatch, with a clear path to select Default. Inspect `src/tickets/ticket-workflow-service.ts` and its options route so an active thread's options follow its pinned provider and a future phase uses the global selection when it creates an agent. Preserve permission selections and review how `AgentCatalogError` and `unsupported-settings` reach the ticket UI.
- Keep OpenAI account polling and quota reporting for existing OpenAI work. Exclude Ollama turns from OpenAI pricing and quota attribution. The shared usage tracker in `src/codex/codex-usage-client.ts` is called before dispatch and samples account quotas. Pass provider information or gate that call at the dispatch boundary. Preserve existing historical cost records and keep normal agent progress and context events for both providers.
- Verify that a configured custom provider receives no OpenAI credentials even when Forge has a ChatGPT login. `requires_openai_auth = false` and a successful account read do not prove what is sent over HTTP. Check the pinned runtime or capture outbound headers using an isolated fake endpoint and synthetic credentials. Treat this as a release check. Never use the owner's credentials in a probe.
- Exercise Plan mode, manual approvals, and `Approve for me` separately before claiming support. Keep permission policy explicit and preserve the owner's permission choice. If a permission mode proves unavailable for Ollama, report it clearly and require an explicit supported choice before execution.
